1. OVERVIEW: THE 3-LAYER ARCHITECTURE
================================================================================

┌─────────────────────────────────────────────────────────────────┐
│                     USER INTERFACE (What users see)             │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │           PRESENTATION LAYER (lib/features/*/presentation) │  │
│  │                                                            │  │
│  │  • Screens (UI widgets)                                   │  │
│  │  • Providers (State management)                           │  │
│  │  • Widgets (Reusable UI components)                       │  │
│  │                                                            │  │
│  │  DEPENDS ON ↓ Domain Layer                               │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
                              ↓ ↑
                         (forwards calls)
                         (receives data)
┌─────────────────────────────────────────────────────────────────┐
│                  BUSINESS RULES (What can be done)              │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │              DOMAIN LAYER (lib/features/*/domain)         │  │
│  │                                                            │  │
│  │  • Entities (Pure business objects)                       │  │
│  │  • Repository Interfaces (Contracts)                      │  │
│  │  • Use Cases (Business operations)                        │  │
│  │                                                            │  │
│  │  ZERO DEPENDENCIES (Pure Dart, no Flutter/DB)            │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
                              ↓ ↑
                         (requests data)
                         (returns data)
┌─────────────────────────────────────────────────────────────────┐
│                 DATA STORAGE (How data is stored)               │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │                DATA LAYER (lib/features/*/data)           │  │
│  │                                                            │  │
│  │  • Models (Database representations)                      │  │
│  │  • Repository Implementations (Actual code)               │  │
│  │  • Data Sources (Database/API connections)                │  │
│  │                                                            │  │
│  │  IMPLEMENTS ↑ Domain Repository Interfaces                │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
                              ↓ ↑
                         (executes SQL)
                         (returns results)
┌─────────────────────────────────────────────────────────────────┐
│                         DATABASE (Drift)                        │
│                   Local SQLite Storage                          │
└─────────────────────────────────────────────────────────────────┘


DEPENDENCY RULE (CRITICAL):
---------------------------
✅ Presentation → Domain (Can import domain)
✅ Data → Domain (Can import domain)
❌ Domain → Presentation (NEVER imports presentation)
❌ Domain → Data (NEVER imports data)

WHY? Domain layer is the CORE. It defines WHAT the app does,
     not HOW it's displayed or WHERE data comes from.

class LandlordCommandScreen extends ConsumerWidget {

  Widget build(BuildContext context, WidgetRef ref) {

          // ✅ DISPLAY system health
          Text('Health: ${stats.systemHealthScore}/100'),
          
          // ✅ HANDLE user tap
          ElevatedButton(
            onPressed: () {

            },
            child: Text('Refresh'),
          ),

WHAT THIS SCREEN DOES:
- Reads stats.projectedRevenue → Displays "RM 14,250.00"
- Reads stats.systemHealthScore → Displays "Health: 85/100"
- User taps "Refresh" → Triggers use case to recalculate

WHAT THIS SCREEN DOESN'T DO:
- Calculate revenue (that's Domain layer)
- Fetch from database (that's Data layer)
- Know about SQL queries (that's Data layer)

3a) ENTITIES - Pure Business Objects
-------------------------------------

WHAT IS AN ENTITY?
An entity represents a REAL-WORLD CONCEPT in your business.

Example: Property Entity
------------------------
File: lib/features/landlord/domain/entities/property.dart

enum PropertyStatus { occupied, vacant, maintenance }

class Property {
  final String id;
  final String address;
  final int totalUnits;
  final int occupiedUnits;
  final double monthlyRent;
  
  Property({
    required this.id,
    required this.address,
    required this.totalUnits,
    required this.occupiedUnits,
    required this.monthlyRent,
  });
  
  // ✅ BUSINESS LOGIC: Calculations belong here
  double get occupancyRate {
    if (totalUnits == 0) return 0;
    return (occupiedUnits / totalUnits) * 100;
  }
  
  double get potentialRevenue => monthlyRent * totalUnits;
  
  double get actualRevenue => monthlyRent * occupiedUnits;`
  
  bool get isFullyOccupied => occupiedUnits == totalUnits;
}

WHY THIS DESIGN?
- Property knows how to calculate its OWN occupancy rate
- No need for external "calculator" functions
- Self-contained: property.occupancyRate (clean API)

ONE USE CASE = ONE ACTION

Example: Get Dashboard Stats Use Case
--------------------------------------
File: lib/features/landlord/domain/usecases/get_dashboard_stats.dart

class DashboardStats {
  final double projectedRevenue;
  final int occupiedUnits;
  final int totalUnits;
  final int systemHealthScore;
  
  DashboardStats({...});
}

class GetDashboardStats {
  final PropertyRepository propertyRepository;
  final FinancialRepository financialRepository;
  
  GetDashboardStats({
    required this.propertyRepository,
    required this.financialRepository,
  });
  
  // ✅ EXECUTE: The main business logic
  Future<DashboardStats> execute(String landlordId) async {
    // Step 1: Fetch raw data
    final properties = await propertyRepository.getPropertiesByLandlord(landlordId);
    final financials = await financialRepository.getSummary(landlordId);
    
    // Step 2: Calculate occupancy
    final totalUnits = properties.fold<int>(0, (sum, p) => sum + p.totalUnits);
    final occupied = properties.fold<int>(0, (sum, p) => sum + p.occupiedUnits);
    
    // Step 3: Custom business logic (health score)
    final occupancyRate = (occupied / totalUnits) * 100;
    final healthScore = _calculateSystemHealth(
      occupancyRate: occupancyRate,
      profitMargin: financials.profitMargin,
    );
    
    // Step 4: Return result
    return DashboardStats(
      projectedRevenue: financials.projectedRevenue,
      occupiedUnits: occupied,
      totalUnits: totalUnits,
      systemHealthScore: healthScore,
    );
  }
  
  // ✅ PRIVATE: Business calculation algorithm
  int _calculateSystemHealth({
    required double occupancyRate,
    required double profitMargin,
  }) {
    int score = 100;
    
    // Business rule: Penalize low occupancy
    if (occupancyRate < 75) score -= 20;
    else if (occupancyRate < 90) score -= 10;
    
    // Business rule: Penalize low profit
    if (profitMargin < 10) score -= 20;
    else if (profitMargin < 20) score -= 10;
    
    return score.clamp(0, 100);
  }
}

WHY USE CASES?
- Encapsulates complex business logic
- Easy to test (mock repositories)
- Can be reused (called from multiple screens)
- Single responsibility (one action)

4a) MODELS - Database Representations

WHAT IS A MODEL?
A class that knows how to convert between:
- Entity (business object) ↔ Database row

Example: Property Model (Drift Table)
--------------------------------------
File: lib/features/landlord/data/models/property_model.dart

import 'package:drift/drift.dart';
import '../../domain/entities/property.dart';

// ✅ DATABASE TABLE DEFINITION
@DataClassName('PropertyData')
class Properties extends Table {
  IntColumn get id => integer().autoIncrement()();
  TextColumn get landlordId => text()();
  TextColumn get address => text()();
  IntColumn get totalUnits => integer()();
  IntColumn get occupiedUnits => integer()();
  RealColumn get monthlyRent => real()();
  DateTimeColumn get createdAt => dateTime()();
}

// ✅ CONVERT: Database → Entity
extension PropertyDataX on PropertyData {
  Property toEntity() {
    return Property(
      id: id.toString(),
      address: address,
      totalUnits: totalUnits,
      occupiedUnits: occupiedUnits,
      monthlyRent: monthlyRent,
    );
  }
}

// ✅ CONVERT: Entity → Database
extension PropertyX on Property {
  PropertyData toData() {
    return PropertyData(
      id: int.parse(id),
      address: address,
      totalUnits: totalUnits,
      occupiedUnits: occupiedUnits,
      monthlyRent: monthlyRent,
    );
  }
}

WHY TWO CONVERSIONS?
- Database uses PropertyData (Drift-specific)
- Domain uses Property (pure Dart)
- Models know how to translate between them


4b) DATA SOURCES - Direct Database Access
------------------------------------------

WHAT IS A DATA SOURCE?
The class that executes actual SQL queries.

Example: Property Local Data Source (DAO)
------------------------------------------
File: lib/features/landlord/data/datasources/property_local_datasource.dart

@DriftAccessor(tables: [Properties])
class PropertyDao extends DatabaseAccessor<AppDatabase> 
    with _$PropertyDaoMixin {
  
  PropertyDao(AppDatabase db) : super(db);
  
  // ✅ SQL: Get all properties for a landlord
  Future<List<PropertyData>> getByLandlord(String landlordId) {
    return (select(properties)
      ..where((p) => p.landlordId.equals(landlordId)))
      .get();
  }
  
  // ✅ SQL: Get single property
  Future<PropertyData> getById(int id) {
    return (select(properties)
      ..where((p) => p.id.equals(id)))
      .getSingle();
  }
  
  // ✅ SQL: Insert new property
  Future<int> insert(PropertyData property) {
    return into(properties).insert(property);
  }
  
  // ✅ SQL: Update existing property
  Future<bool> update(PropertyData property) {
    return update(properties).replace(property);
  }
}

DRIFT GENERATES SQL:
- select(properties) → SELECT * FROM properties
- where(...) → WHERE landlord_id = ?
- get() → Execute query


4c) REPOSITORY IMPLEMENTATION - Glue Between Domain & Data
-----------------------------------------------------------

WHAT IS A REPOSITORY IMPLEMENTATION?
The class that IMPLEMENTS the domain repository interface.

Example: Property Repository Implementation
--------------------------------------------
File: lib/features/landlord/data/repositories/property_repository_impl.dart

import '../../domain/repositories/property_repository.dart';
import '../../domain/entities/property.dart';
import '../datasources/property_local_datasource.dart';

// ✅ IMPLEMENTS domain interface
class PropertyRepositoryImpl implements PropertyRepository {
  final PropertyDao dao;
  
  PropertyRepositoryImpl(this.dao);
  
  @override
  Future<List<Property>> getPropertiesByLandlord(String landlordId) async {
    // Step 1: Get database rows
    final dataList = await dao.getByLandlord(landlordId);
    
    // Step 2: Convert to entities
    return dataList.map((data) => data.toEntity()).toList();
  }
  
  @override
  Future<Property?> getPropertyById(String propertyId) async {
    try {
      final data = await dao.getById(int.parse(propertyId));
      return data.toEntity();
    } catch (e) {
      return null; // Not found
    }
  }
  
  @override
  Future<void> addProperty(Property property) async {
    await dao.insert(property.toData());
  }
  
  @override
  Future<void> updateProperty(Property property) async {
    await dao.update(property.toData());
  }
  
  @override
  Future<int> getTotalOccupiedUnits(String landlordId) async {
    final properties = await getPropertiesByLandlord(landlordId);
    return properties.fold(0, (sum, p) => sum + p.occupiedUnits);
  }
}

FLOW:
1. Use case calls: propertyRepository.getPropertiesByLandlord('123')
2. Repository calls: dao.getByLandlord('123')
3. DAO executes SQL: SELECT * FROM properties WHERE landlord_id = '123'
4. DAO returns: List<PropertyData> (database rows)
5. Repository converts: PropertyData → Property (entities)
6. Use case receives: List<Property> (pure business objects)

    // Fetch properties

COMPLETE DATA FLOW:
------------------

1. Screen watches portfolioPropertiesProvider
   ↓
2. Provider calls GetProperties use case
   ↓
3. Use case calls repository.getPropertiesByLandlord('landlord_123')
   ↓
4. Repository calls dao.getByLandlord('landlord_123')
   ↓
5. DAO executes SQL: SELECT * FROM properties WHERE landlord_id = 'landlord_123'
   ↓
6. Database returns: List<PropertyData> (rows)
   ↓
7. Repository converts: PropertyData → Property (entities)
   ↓
8. Use case sorts: properties.sort((a, b) => ...)
   ↓
9. Provider returns: List<Property>
   ↓
10. Screen displays: PropertyCard widgets

SUMMARY: WHY THIS MATTERS FOR RESIDEX
================================================================================

RIGHT NOW (Phase 1.5):
---------------------
✅ You have beautiful UI (5 landlord screens)
✅ You have mock data (hardcoded in providers)
✅ Everything LOOKS good, but no real data

PROBLEM:
--------
- If you add database code directly to screens → MESSY
- If you put business logic in UI → HARD TO TEST
- If you mix everything → IMPOSSIBLE TO MAINTAIN

SOLUTION (Clean Architecture):
------------------------------
1. DOMAIN LAYER: Write business rules ONCE (pure Dart)
2. DATA LAYER: Implement database ONCE (Drift)
3. PRESENTATION: Screens just DISPLAY (no logic)

RESULT:
-------
✅ Change UI → No impact on business logic or database
✅ Change database → No impact on UI or business logic
✅ Change business rules → Update one use case only
✅ Test each layer independently
✅ Multiple developers can work simultaneously
✅ Easy to add new features (rex AI, tenant features)

----------

2. Copy repository interfaces
3. Copy use case code
4. Update providers to use use cases (instead of mock data)
5. Build data layer (Week 5-6)

FINAL ANALOGY:
-------------
Think of your app as a RESTAURANT:

PRESENTATION LAYER = WAITERS
- Take orders from customers (users)
- Serve food (display data)
- Don't cook food themselves

DOMAIN LAYER = RECIPES & CHEF
- Define HOW to cook (business logic)
- Decide WHAT dishes can be made
- Don't care about where ingredients come from

DATA LAYER = KITCHEN & SUPPLIERS
- Store ingredients (database)
- Fetch ingredients when needed
- Follow recipes from chef

CLEAN ARCHITECTURE = Well-organized restaurant
- Customers never enter kitchen
- Chef never serves customers
- Kitchen never invents recipes

Each role has ONE responsibility. That's why it works! 🍽️
